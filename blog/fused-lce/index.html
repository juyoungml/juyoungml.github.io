Fused Linear Cross-Entropy

Why fusing the LM head projection with cross-entropy is the single biggest memory win for training LLMs at long context.

Share:X·LinkedIn·

Claim

For a vocabulary of size VVV and a batch of N=B⋅TN = B \cdot TN=B⋅T tokens, the standard "linear → softmax → NLL" path materializes an N×VN \times VN×V logits tensor in float32 just to throw it away one row at a time. Fusing the projection with the loss removes that tensor from peak memory entirely, with no change to the gradient.

Why the logits tensor dominates

Take a 7B model trained at T=8192T = 8192T=8192 on a Llama-3 tokenizer with V≈128kV \approx 128\text{k}V≈128k. The LM head is W∈RV×dW \in \mathbb{R}^{V \times d}W∈RV×d and the logits are shaped [N,V][N, V][N,V].

At per-rank micro-batch B=1B = 1B=1, the logits in float32 occupy

8192×128000×4 B  ≈  4.2 GiB,8192 \times 128000 \times 4\,\text{B} \;\approx\; 4.2\,\text{GiB},8192×128000×4B≈4.2GiB,

with another 4.2 GiB for ∂L/∂logits\partial L / \partial \text{logits}∂L/∂logits during backward. The hidden activations entering the head are 8192×4096×2 B≈67 MiB8192 \times 4096 \times 2\,\text{B} \approx 67\,\text{MiB}8192×4096×2B≈67MiB in bfloat16, and the weight matrix itself is ≈1 GiB\approx 1\,\text{GiB}≈1GiB in bfloat16.

So we pay roughly 8 GiB of activation memory to compute a scalar loss. The logits are written, read once for the softmax, and then thrown away. Every other activation in the model is smaller than this one tensor.

Setup

The unfused path computes

ℓi=−log⁡softmax(Whi)yi,L=1N∑iℓi,\ell_i = -\log \mathrm{softmax}(W h_i)_{y_i}, \qquad L = \frac{1}{N}\sum_i \ell_i,ℓi​=−logsoftmax(Whi​)yi​​,L=N1​i∑​ℓi​,

storing the full logits zi=Whi∈RVz_i = W h_i \in \mathbb{R}^Vzi​=Whi​∈RV before reducing.

Cross-entropy reduces to a scalar per token, so the full ziz_izi​ never needs to be resident at once. The gradient w.r.t. logits has the familiar form

∂L∂zi  =  1N(softmax(zi)−eyi),\frac{\partial L}{\partial z_i} \;=\; \frac{1}{N}\bigl(\mathrm{softmax}(z_i) - e_{y_i}\bigr),∂zi​∂L​=N1​(softmax(zi​)−eyi​​),

so per-token contributions to ∂L/∂hi\partial L/\partial h_i∂L/∂hi​ and ∂L/∂W\partial L/\partial W∂L/∂W can be accumulated row-by-row without ever materializing the full [N,V][N, V][N,V] tensor.

The fused kernel

Stream over rows of hhh in chunks of size CCC. For each chunk:

  1. Compute z=h[c:c+C]W⊤∈RC×Vz = h_{[c:c+C]} W^\top \in \mathbb{R}^{C \times V}z=h[c:c+C]​W⊤∈RC×V in bf16.
  2. Compute lsei=log⁡∑jezij\mathrm{lse}_i = \log \sum_j e^{z_{ij}}lsei​=log∑j​ezij​ in fp32, accumulate ℓi=lsei−zi,yi\ell_i = \mathrm{lse}_i - z_{i, y_i}ℓi​=lsei​−zi,yi​​.
  3. Form pij=ezij−lseip_{ij} = e^{z_{ij} - \mathrm{lse}_i}pij​=ezij​−lsei​ in place; subtract one at column yiy_iyi​.
  4. Accumulate ∂L/∂h[c:c+C]+=p W\partial L/\partial h_{[c:c+C]} \mathrel{+}= p\, W∂L/∂h[c:c+C]​+=pW and ∂L/∂W+=p⊤h[c:c+C]\partial L/\partial W \mathrel{+}= p^\top h_{[c:c+C]}∂L/∂W+=p⊤h[c:c+C]​.
  5. Free ppp, zzz. Move to the next chunk.

Peak logits memory drops from N⋅VN \cdot VN⋅V to C⋅VC \cdot VC⋅V. With C=1024C = 1024C=1024 and V=128kV = 128\text{k}V=128k, that's 512 MiB instead of 4.2 GiB during forward, and the backward grad tensor is reused in place so the saving doubles.

Implementation sketch

import torch

def fused_lce(h, W, targets, chunk_size=1024):
    # h: (N, d) bf16, requires_grad
    # W: (V, d) bf16, requires_grad
    # targets: (N,) int64
    N = h.shape[0]
    loss = h.new_zeros((), dtype=torch.float32)
    grad_h = torch.zeros_like(h)
    grad_W = torch.zeros_like(W)

    for c in range(0, N, chunk_size):
        end = min(c + chunk_size, N)
        h_c = h[c:end]
        y_c = targets[c:end]

        z = h_c @ W.T                                  # (C, V) bf16
        z_f = z.float()
        lse = torch.logsumexp(z_f, dim=-1)             # (C,) fp32
        nll = lse - z_f.gather(1, y_c[:, None]).squeeze(1)
        loss += nll.sum()

        p = (z_f - lse[:, None]).exp_()                # softmax, fp32
        p.scatter_add_(1, y_c[:, None], -torch.ones_like(p[:, :1]))

        grad_h[c:end] = (p @ W.float()).to(h.dtype)
        grad_W += (p.T @ h_c.float()).to(W.dtype)

    loss /= N
    grad_h /= N
    grad_W /= N
    return loss, grad_h, grad_W

The above is the pedagogical version. A production implementation is a Triton or CUDA kernel that fuses steps 1 through 4 inside one tile, so the C×VC \times VC×V block of ppp never leaves SRAM. Liger and Apple's Cut Cross-Entropy both do this, with different choices around bf16 vs fp32 accumulation and how the softmax is stabilized across tiles.

The runtime overhead is small because the projection is memory-bound at V=128kV = 128\text{k}V=128k; chunking trades a bit of kernel-launch overhead for a much smaller resident footprint. In return you get headroom for longer context, less aggressive activation checkpointing, or both.

Caveats

Gotcha

The single most common bug here is forgetting the fp32 cast on the softmax. It compiles, it runs, the loss curve looks fine for a thousand steps, and then it slowly diverges from the unfused baseline. Always test against the unfused reference at small scale before trusting the kernel.

  • Numerical stability. The softmax must be computed in fp32 with the standard logsumexp trick. Skipping the fp32 cast silently degrades training loss on long sequences.
  • Label smoothing, z-loss, auxiliary losses. All are linear in the logits or in ppp, so they fit cleanly into the same loop. The popular (lse)2(\mathrm{lse})^2(lse)2 z-loss only needs lse\mathrm{lse}lse, which you already compute in step 2.
  • Weight tying. If the head shares weights with the input embedding, grad_W accumulates into the same parameter; the embedding-lookup gradient from the input side adds on top.
  • Sequence parallelism. The chunked loop runs along the token axis, so it composes with sequence-parallel layouts. Just be careful to reduce loss and grads consistently across the sequence shards.
